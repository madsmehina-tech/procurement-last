# خطة التجربة الميدانية (3 أيام عمل)

**الهدف:** التأكد عمليًا قبل الاعتماد وإيقاف الأنظمة القديمة. تُجرى على **نسخة تجريبية (Staging)** بجانب النظام الحقيقي، فلا خطر على بياناتك.

## اليوم صفر: التجهيز (ساعة)
1. انسخ قاعدة البيانات إلى اسم جديد: `PurchaseSystem_STAGING.accdb`.
2. `copy config.staging.ini.example config.staging.ini` وعدّل المسارات (القاعدة المنسوخة، مجلد أرشيف تجريبي، المنفذ 5001).
3. شغّل `deploy\migrate_staging.bat` (يحدّث نسخة الاختبار فقط).
4. شغّل `deploy\start_staging.bat`. سيظهر شريط أصفر «بيئة تجريبية» أعلى كل صفحة.
5. نفّذ `python tools\setup_check.py` و`python tools\check_storage.py` وأرسل لي نتيجتهما.

## ملخّص آلي في نهاية كل يوم
```
python tools\uat_report.py 2026-10-12      ← غيّر التاريخ لليوم المطلوب
```
يعطيك: عدد الطلبات والأجهزة، وزمن الاستجابة (الوسيط و95%)، وأبطأ الصفحات، والأخطاء.

## معايير القبول (كلها مطلوبة)
- أخطاء الخادم (5xx) = 0، و`error.log` فارغ أو أخطاؤه مفسَّرة ومعالجة.
- 95% من الطلبات أسرع من 2 ثانية (من تقرير UAT).
- `check_storage` تقييمه «ممتاز» أو «مقبول».
- لا ملف مفقود ولا مكتوب فوقه في أي سيناريو.
- كل السيناريوهات العشرين ✔.

## تسجيل الملاحظات
اكتب لكل مشكلة: رقم السيناريو · الجهاز · الوقت التقريبي · ما حدث · لقطة شاشة. أرسلها لي مجمّعة آخر كل يوم وأصلحها قبل اليوم التالي.

## بعد النجاح: الانتقال للنظام الحقيقي
1. أوقف النسخة التجريبية.
2. ضع في `config.ini` (الحقيقي) مسارات الإنتاج، ونفّذ `python migrate.py`.
3. **ابدأ من قاعدتك الحقيقية** (لا تنقل بيانات الاختبار)، أو انقل نسخة staging فقط إذا كان الفريق أدخل فيها عملًا فعليًا تريد الإبقاء عليه.
4. فعّل `install_autostart.bat` والنسخ الاحتياطي اليومي.
5. أوقف الأنظمة القديمة بعد أسبوع من العمل المستقر، مع الاحتفاظ بنسخة منها للأرشيف.
